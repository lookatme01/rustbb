# Code review — 2026-10-09

Five classes of confirmed problems were fixed. The review concentrated on search,
forum visibility, guest caching, password work, image processing and their request
and background-task lifetimes. Related code inspected included forum listings,
stored results, online locations, attachments, storage, feeds and statistics.

| Priority | Finding | Fix |
| --- | --- | --- |
| P1 | Archive forum listings used uid 0 to mean both “guest with own threads only” and “unrestricted”. Guests could see other members’ thread titles. The raw group flag also restricted moderators unnecessarily. | Resolve own-thread restrictions through shared forum access, reject guests in own-thread forums, and count only the member’s eligible threads for pagination. |
| P1 | API full-text search bypassed the browser search semaphore and SQL timeout. Concurrent expensive requests could occupy database connections without a bounded query lifetime. | Share the eight-search semaphore and apply a transaction-local five-second statement timeout. Return a useful validation error on timeout. |
| P1 | Image and Argon2 permits lived in the async request future. Cancelling the request released the permit while `spawn_blocking` continued, allowing concurrency and memory use to exceed the cap. | Move each permit into the blocking closure so the job retains it through completion, including error paths. |
| P2 | Thread-mode full-text search limited matching posts before deduplicating threads. A busy thread crowded out other matches, and sorting operated on the incomplete candidate set. An empty sort field also ignored ascending order. | Use a thread query with `EXISTS` for matching posts. Apply the requested thread sort before limiting distinct threads. |
| P2 | Guest-cache tag generations persisted forever, independent of entry TTL and the HTML memory budget. Every newly invalidated thread/forum added permanent metadata. | Bound generations to 10,000 tags; clear entries and generations together when the limit is reached or the cache is globally cleared. Preserve epoch checks for in-flight renders. |

## Regressions

- A busy thread with 160 matching posts cannot crowd out another match with a 50-thread limit. Ascending, descending, implicit last-post and subject ordering are checked.
- API search waits while all shared search slots are occupied.
- An exclusive lock on `posts` triggers the API statement timeout; a subsequent request succeeds after the lock is released.
- Cancelling an image request leaves the blocking job’s image slot occupied until the job finishes.
- More than 10,000 unique tag invalidations do not grow metadata beyond its cap, revive old entries, or admit old renders.
- Archive own-thread restrictions are checked for guests, the thread owner, other members and administrators.

## Performance check

A read-only `EXPLAIN (ANALYZE, BUFFERS)` on the existing `rbb_load` database
(approximately 300,000 threads and 3,010,000 posts) tested the final semi-join
shape with the common words `rust database`, readable forum IDs 8–78 and a
500-thread limit. PostgreSQL used `threads_lastpost` and `posts_tid_dateline`,
returned 500 distinct threads, and reported 1,011.990 ms execution time with
58,035 shared-buffer hits. The machine was also compiling other Rust jobs.
This is one warm-cache SQL sample, not an endpoint throughput benchmark.

The earlier grouping implementation exceeded an eight-second benchmark timeout
and was replaced before delivery. The final query retains the existing five-second
production timeout; broad or unusual sort requests can still reach that limit.
No database migrations or persisted load-data changes were needed.

## Security pass: attachment abuse

Concurrent requests could bypass both account storage quotas and per-post
attachment limits: a deterministic database gate reproduced two successful
700-byte uploads against a 1,024-byte quota, and two successful uploads against
a one-attachment limit. The upload now acquires transaction-scoped PostgreSQL
advisory locks for the account and existing post, repeats the checks under those
locks, and commits the attachment plus parser invalidation together. This works
across application nodes sharing the database. Lock waits are bounded to two
seconds and return a retry message. Existing moderator limit exemptions remain.

An early check still rejects exhausted quotas before image decoding, without
holding a database connection through CPU work. The streaming ceiling also
respects the account's total quota. Temporary-file cleanup remains active until
storage completes, including storage failures. These changes do not make database
and external file storage a single atomic system; cleanup of already-stored files
following cancellation or database failure remains a separate hardening target.

The dependency advisory check passed the current repository policy, which retains
its existing documented exceptions in `deny.toml`; no new exceptions were added.

Production configuration priorities verified against the code:

- Set finite attachment quotas for untrusted member groups (`attachquota`, in KB);
  zero means unlimited. The new synchronization enforces configured limits.
- Enroll administrators in TOTP at `/usercp/security`, then enable the existing
  **Require 2FA for Admin CP** setting (`acp2fa`). Its installation default is off.
- Serve the board over HTTPS and set `RBB_SECURE_COOKIES=true`; this enables secure
  cookies and the HSTS response header. The default supports local HTTP development.
- Configure `RBB_TRUSTED_PROXIES` with the actual proxy networks so client addresses
  used by throttles cannot be forged through forwarding headers.

These are deployment checks, not assertions about the current live configuration.
No live deployment settings were inspected or changed during this pass.
